## Executive Summary

This paper investigates a critical problem for multi-agent development systems: **specification portability across heterogeneous LLM agents**. Using Oracle-to-PostgreSQL database migration as a controlled transformation task, researchers evaluate whether specifications generated by one agent can be effectively executed by other agents. The findings show that cross-agent transfer produces substantial performance degradation, challenging the assumption that specifications alone enable seamless agent interoperability. This work has direct implications for building resilient multi-agent development systems where specifications should be portable across agent implementations.

## Problem Statement

As organizations deploy multiple LLM-based development agents (Claude Code, GitHub Copilot, Google Gemini, Amazon Kiro, etc.), a critical interoperability challenge emerges:

**The Specification Portability Problem:**
- **Scenario:** Agent A generates a specification for a code migration task; Agent B is expected to implement from that specification
- **Challenge:** Specifications may be tailored to a particular agent's reasoning style, and cross-agent transfer may degrade implementation quality
- **Scale:** Enterprise systems run millions of development tasks across multiple agents; ensuring specification reusability is essential for cost optimization and flexibility
- **Complexity:** Different agents have varying capabilities, model sizes, training data, and instruction-following behaviors

**Research Gap:** Can formal specifications enable deterministic, agent-independent code migration? What are the sources of cross-agent degradation?

## Core Concepts & Theory

### Specification-Driven Development Paradigm

The paper operates within the **specification-first** development model:
1. **High-Level Specification:** Input database schema (source and target formats)
2. **Logical Specification:** Intermediate representation defining the transformation rules
3. **Implementation:** Agent-generated code (PL/SQL → PostgreSQL)

### Evaluation Dimensions

The paper employs multiple fidelity levels for specification quality assessment:

1. **Syntactic Correctness:** Token F1 score, exact token matching
2. **Structural Equivalence:** AST (Abstract Syntax Tree) exact match, AST mean similarity
3. **Semantic Correctness:** Immediate runnability in PostgreSQL 16
4. **Agent-Level Consistency:** Cross-agent performance variance analysis

## Main Ideas & Contributions

### 1. Specification-First Migration Pipeline

The core contribution is a **two-stage specification pipeline**:

**Stage 1: Native Specification Generation**
- Oracle database schema as input
- Agent generates intermediate specifications
- Specifications capture: data type mappings, transformation logic, constraints
- Evaluation: 1,006 PL/SQL files → 623 successfully regenerated (62% success) → 380 executable (38% end-to-end success)

**Stage 2: Cross-Agent Implementation**
- 1,802 Oracle scripts with reference PostgreSQL implementations
- Five agents attempt implementation from specification:
  - **Single-agent baseline:** Claude Code, Cursor (initial evaluation)
  - **Cross-agent:** Amazon Kiro, Google Gemini, GitHub Copilot
- Each agent receives the specification and implements independently

### 2. Cross-Agent Degradation Patterns

**Key Finding:** Specification size does NOT predict implementation quality

**Observed Degradation Sources:**
- **Model-Specific Reasoning:** Larger models (Gemini) vs. specialized models (Copilot for code)
- **Instruction Sensitivity:** Different agents interpret specifications with varying fidelity
- **Context Window Limitations:** Long specifications may exceed agent context budgets
- **Training Data Distribution:** Agents trained on different corpora may favor different SQL dialects

### 3. Native vs. Foreign Specifications

The paper distinguishes:
- **Native Specification:** Generated and implemented by the same agent (baseline performance)
- **Foreign Specification:** Generated by Agent A, implemented by Agent B (transfer performance)

**Critical Insight:** Foreign specifications show "substantial agent-dependent degradation," suggesting that agent-specific reasoning patterns leak into specifications even when attempting to create formal, universal representations.

### Metrics

| Metric | Definition | Sensitivity |
|--------|-----------|------------|
| **Token F1** | Precision/Recall on generated tokens | Syntactic surface form |
| **Exact Match** | Perfect string match to reference | Overly strict (formatting) |
| **SQL Syntax Validity** | Passes PostgreSQL parser | Coarse-grained |
| **AST Exact Match** | Identical Abstract Syntax Trees | Semantic structure |
| **AST Mean Similarity** | Average similarity across tree nodes | Partial credit for close matches |
| **Immediate Runnability** | Query executes without errors | Gold standard |

### Implementation

The specification pipeline operates as:
```
For each Oracle PL/SQL file:
  1. Parse schema and type information
  2. Generate specification (agent-dependent)
  3. For each target agent:
     a. Feed specification as context
     b. Request PostgreSQL implementation
     c. Evaluate using 6 metrics
     d. Record success/failure + metrics
```

### Key Finding: Specification Size ≠ Implementation Quality

**Counterintuitive Result:** Agent-generated specifications with high token counts and complexity do not correlate with successful downstream implementation. This suggests:
- Verbosity in specifications may introduce ambiguity
- Agents struggle to generate universally interpretable specifications
- Specification artifacts encode agent-specific reasoning styles

### Cross-Agent Degradation Patterns

**Agent Performance Variance:**
- Single-agent (native specification + implementation): 38% baseline
- Cross-agent transfer produces "substantial agent-dependent degradation"
- Magnitude of degradation varies by agent pair and specification complexity

**Interpretation:** Specifications are not truly universal; they are partially agent-specialized. Cross-agent transfer fails because:
1. Specifications assume recipient agent's reasoning patterns
2. Different agents prioritize different aspects of specifications
3. Incomplete specifications require implicit domain knowledge

## Practical Applications & Use Cases

### 1. Enterprise Agent Fleet Management

**Scenario:** Company runs both Claude Code and GitHub Copilot for different development tasks.

**Problem:** When Claude Code generates migration specs, Copilot underperforms (higher error rates).

**Solution:** This paper's findings suggest using homogeneous agent fleets for critical tasks OR designing specifications explicitly for cross-agent transfer.

### 2. Cost Optimization in Multi-Agent Systems

**Scenario:** Organizations want to use cheaper agents (e.g., Gemini) for specification generation and expensive agents (e.g., Copilot) only for implementation when needed.

**Problem:** Specification-first workflow assumes specs are universal.

**Finding:** Cross-agent transfer degrades performance, suggesting different agents should own different pipeline stages.

### 3. Specification Quality Standards

**Current Assumption:** Formal specifications enable agent-independent development.

**Reality:** Specifications leak agent-specific reasoning patterns.

**Implication:** Development standards must account for agent heterogeneity; "universal specs" may be unattainable at current model sophistication levels.

### 4. Multi-Agent Workflow Design

**Best Practice:** When using multiple agents:
- **Stage 1 (Specification):** Assign to strongest model
- **Stage 2 (Implementation):** Assign same or compatible model
- **Alternative:** Explicitly train agents to generate specifications compatible with target agents

## Insights & Implications

### 1. Interoperability is Harder Than Assumed

The finding that specification size does NOT predict implementation quality suggests that current LLM-based agents have **implicit, non-transferable reasoning patterns**. Achieving true interoperability requires either:
- Explicit specification standardization (e.g., formal methods)
- Agent training to generate universally interpretable specifications
- Accepting cross-agent performance degradation

### 2. Agent Specialization vs. Generalization Trade-off

Agents optimized for specification generation may not generate specifications optimal for other agents. This mirrors compiler optimization: **code generated for one target architecture may be suboptimal on another**.

### 3. Research Questions Opened

- Can specifications be explicitly designed to minimize cross-agent degradation?
- Do larger models generate more transferable specifications?
- What specification formats (formal languages, structured data, natural language) maximize cross-agent compatibility?
- Can agents be trained to generate agent-agnostic specifications?

### 4. Limitations in Specification-Driven Development

The paper demonstrates that specification-driven software development (a key abstraction for multi-agent systems) has fundamental limitations when agents are heterogeneous. Implications:
- **For frameworks:** MCP (Model Context Protocol) and similar standards must account for agent-specific reasoning
- **For tools:** IDE-based agent assistants should prefer homogeneous agent stacks for critical tasks
- **For research:** Development of **specification formats explicitly optimized for cross-agent transfer** is an open research area

## Significance to Agentic Software Development

This paper is a sobering reality check for **multi-agent development systems**: the assumption that **formal specifications enable agent-independent development is partially false**. In practice, agent heterogeneity introduces subtle but significant degradation in specification-driven workflows.

**For developers building agent-based development tools:**
- Do not assume specs are universally transferable
- Consider explicit agent pairing strategies in multi-agent workflows
- Invest in specification formats designed for cross-agent compatibility
- Plan for performance trade-offs when using heterogeneous agent fleets

**For researchers:** This opens a research agenda on **specification design for multi-agent systems** — how to create specifications that remain high-fidelity across diverse agent implementations.
